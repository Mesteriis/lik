# Persistent media catalog

Tasks 5–7 implement the Room 2.8.4 metadata catalog, Paging 3.5.1 feed, and organization/search in the single `:app` module. KSP 2.3.9 generates the DAO implementation; schemas 1, 2, and 3 are checked into `app/schemas/`, with explicit non-destructive migrations. This is original Lik code using official Android/Room/Paging APIs, with no code copied from gallery references. These are Apache-2.0 dependencies, unrelated to model licenses.

## Ownership and identity

`PhotoStore` remains the owner of committed private files, validation, import, and deletion. Room stores only an opaque private file ID and resolves it through `PhotoStore.fileFor`; no image is moved or duplicated by catalog migration. Device originals remain in MediaStore and are referenced through volume-specific content URIs.

Imported internal IDs remain the existing lowercase SHA-256 values. Device IDs are prefixed hashes of a length-framed `(volume, MediaStore version, row ID, generation added)` tuple. Content revision uses `GENERATION_MODIFIED` and does not change object identity. A reused row in another volume, after a MediaStore version reset, or with another creation generation receives a distinct ID. Old records remain inaccessible, preserving metadata and user relationships. Display name, timestamps, and cross-source content similarity never merge objects.

`MediaScanner` reads each concrete volume with a persisted version/generation/access checkpoint. Changed metadata is queried using `GENERATION_MODIFIED`; a separate two-column identity cursor reconciles removals. Both cursors emit at most 128 objects per application batch and honor `CancellationSignal`. A Room transaction holds each complete scan: cancellation, null cursor, access failure, or a changed final version/generation cannot advance the checkpoint or publish partial removal. A full inventory uses generation zero after a reset or a limited-access transition. Row reuse remains a distinct birth-generation identity. Detached volumes and old versions become inaccessible, not deleted.

The gallery ViewModel coalesces ContentObserver events over 250 ms, cancels superseded scans, reconciles again on resume, and unregisters/cancels foreground observation on stop. Already queued observer callbacks are ignored while stopped; stopping also invalidates pending scan publications. Imports use the same serialized worker and keep their own file ownership. A changing provider version/generation retries up to three complete transactional attempts; cancellation and permission changes are not retried. Source failures retain metadata and render the existing source-error state; cancellation does not become a source error. A separate UUID scan marker proves participation in the inventory without changing the epoch-millisecond meaning of `lastSeenAt`.

## Record contract

`MediaRecord` stores internal ID, source key, volume/version/generation identity, URI or private file ID, nullable name/MIME/dimensions/size, capture/add/modify timestamps, date source and optional original UTC offset, bucket/folder metadata, content revision, availability, and last-seen time. Timestamps are epoch milliseconds. Unknown values stay null in storage; the legacy gallery model still receives its existing zero/empty display defaults. Offsets are evidence from metadata and are never inferred from the current time zone.

Availability is `AVAILABLE`, `INACCESSIBLE`, or `MISSING`. Only a stable complete inventory under full image permission marks an absent row from the same volume/version missing. Limited visibility, denied access, detached volumes, and old versions cannot prove deletion and are inaccessible instead. The full-access state is checked with both scan snapshots. A missing private file is marked missing from PhotoStore's authoritative inventory. Metadata is retained in all cases; reappearance restores availability. No device original is removed by reconciliation.

## Imported-file migration and recovery

There was no previous Room database, so version 1 needs no SQL upgrade migration. `ImportedCatalogMigration` is the file-to-catalog migration, not a destructive database migration. It enumerates only committed `<sha256>.image` files and reads file size/mtime; it does not open or decode image content. Unknown original names, MIME, dimensions, and capture dates stay unknown. Interrupted `.part` and unrelated files are excluded.

The repository holds PhotoStore's writer monitor while applying the inventory in one Room transaction. Insert-if-absent preserves existing identities and enriched metadata; marking seen updates availability and last-seen time. A failed transaction rolls back the inventory. No completion flag is needed: every refresh safely retries, including a crash after file commit but before catalog registration. A failed directory listing throws instead of being treated as an empty library. The files are never changed by a catalog transaction.

The gallery load boundary catches imported-inventory I/O and access failures after transaction rollback. It returns previously available catalog rows with an explicit imported-source error, skips file enrichment for that failed inventory, and lets the screen finish scanning. The notice explains that some cached photos may be temporarily unavailable. A subsequent successful refresh clears the error. Device-source errors remain separate.

Imported-file revision/size changes invalidate cached EXIF while preserving identity and the original added time. Optional EXIF enrichment caches capture date, explicit offset, orientation, and a negative result by content revision. A refresh enriches up to 60 pending imports; the viewer enriches its requested import or device URI on demand. Enrichment is intentionally lazy: opening a large library does not parse every file. Device inventory metadata comes from MediaStore. Failed I/O or URI access is not cached as absent EXIF, and revision checks reject stale enrichment writes. Detailed EXIF presentation remains outside this task.

The library timezone is stored once in `gallery_ui`. Offsetless EXIF wall times and materialized day/week/month/year keys use that zone even when the phone travels. Explicit EXIF offsets take precedence and remain stored evidence. DST overlaps use Java's earlier offset when no offset is present; malformed dates remain unknown. Weeks in the persistent catalog start on ISO Monday. The version-1 migration backfills sort and all period keys for every dated row, including inaccessible/missing rows, inside Room's upgrade transaction using the persisted library zone. It reads at most 256 IDs/timestamps per keyset batch. DAO/Paging access waits for migration commit; an interrupted backfill rolls back the schema and data and retries on the next open. Unknown dates remain undated. App backup rules already exclude the database and private files.

## Bounded feed and viewer

The foreground feed uses Room `PagingSource` through `CatalogPaging` and `AsyncPagingDataDiffer`, with 60-row pages, 15-row prefetch, a 180-record retention target, and no catalog-sized list. Day headers are paging separators, with SQL group counts and positions. Overview levels use SQL aggregates and read at most three cover rows per visible period. The small `ImportState.photos` snapshot is limited to the first 60 records for source/error state; it is not the scrolling data source. Private-file inventory enumeration is still proportional to the number of imported files, without decoding them.

Viewer startup reconciles sources, then queries current/previous/next by stable media ID and the `(sortAt, mediaId)` order. It holds at most three records and advances rapid queued gestures from the last requested ID. Deletion reconciles the private inventory before choosing the next available neighbor. Paging anchors carry catalog rank; a distant ID starts a page near that rank, and a disappeared anchor falls back chronologically. Sorting, grouping, diffs, counts, and provider work stay off the UI thread.

## Organization and conventional search (Task 7)

Schema v3 adds `album`, `album_media`, `favorite`, and `media_tag`. Albums have UUID identity and permit duplicate display names; UI labels include a short ID. Membership and favorites are idempotent primary-key relationships to stable media IDs. Tags preserve original spelling and use NFC plus `Locale.ROOT` Unicode lowercase for comparison. An inaccessible or missing media row keeps all relationships; ordinary results and collection counts include only `AVAILABLE` rows. Removing an album removes its memberships, never photos or files. No code in `Organization.kt` or `OrganizationPanel.kt` owns filesystem or MediaStore mutation.

Device folders are SQL groups keyed by volume, bucket ID, and relative path, so same-named folders on different volumes remain distinct. Search combines literal display-name substring, inclusive UI date interval, source, exact normalized tag, album, favorite, and folder filters. SQL parameters preserve Cyrillic and treat `%`, `_`, and quotes literally. Date filters use capture time with added-time fallback and exclude unknown dates; without date limits unknown dates remain visible. End dates become the next local midnight in the persisted library zone. Stable media ID breaks date/name ties.

Migration v2→v3 backfills `displayNameSearch` in keyset batches of at most 256 inside the Room upgrade transaction, including inaccessible rows. A constructor-body property recomputes that key when source metadata is copied/updated. Interrupted migration rolls back and retries. No destructive fallback is enabled.

Native Albums and Search screens use scrollable text result rows with name, source, date, ID suffix and manual tags, open the existing viewer, and page at 60 rows (+1 for next-page detection). Result thumbnails and grouping albums are not implemented. Search drafts, filters, collection/page and selection survive Activity recreation. Long press selects either source; Organize applies favorite, album, or tag changes after a transactional availability recheck. Delete candidates are separately computed and rechecked, allowing only accessible private imports. Share/export capability contracts are present for Task 8; transport UI remains future work. More routes to explicitly labeled future Trash and AI settings screens. Trash still has no retention/restore behavior in Task 7, and existing private-copy deletion remains permanent.

### Verification scope

JVM tests include source separation, row reuse, framing collisions, unknown metadata, DST/offset parsing, debounce, invalid inventories, and migration retries. Android tests use real Room/SQLite for insert/update/removal, limited visibility, revocation, reset, cancellation rollback, schema migration, and EXIF invalidation. Metadata-only 2k/20k/100k fixtures exercise bounded Room page loads, period counts/covers, and viewer windows without creating physical photo files. An adapter-level paging test starts at a distant identity and checks eviction during scrolling. These are functional scaling checks, not physical Fold latency or memory benchmarks; physical Fold and real Google cloud Share acceptance remain separate.
