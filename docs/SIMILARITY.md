# Exact duplicates and similar photos

Task 12 adds an original Lik implementation of cross-source duplicate and similarity review. It uses Android, Room and WorkManager APIs with a versioned DCT perceptual hash; no model payload or third-party runtime code is added.

The catalog identity contract is unchanged. Imported private copies keep their SHA-256 media ID, while every eligible MediaStore or imported record may receive a `content_fingerprint` bound to its current `contentRevision` and `accessGrantEpoch`. Exact content is a separately streamed SHA-256 digest. Exact duplicates are queried as digest groups and their members use keyset pages; they are never expanded into quadratic pair rows. The digest is independent of perceptual-hash versions. Neither exact nor visual similarity merges, renames or owns a media record.

Perceptual fingerprint v2 decodes at most a 64-pixel edge, converts to luminance, samples 32×32, and stores 63 low-frequency DCT comparisons in eight bytes. Hamming distance at most 14 is the current similarity threshold. Candidate lookup stores 16 disjoint four-bit chunks. If two 64-bit values differ in at most 14 bits, at most 14 chunks can differ, so at least two chunks match; the shared-band query therefore has complete recall within the threshold before exact Hamming verification. This is an implementation threshold, not a measured quality claim.

Visual candidate work is bounded and resumable. SQL returns unique perceptual-hash buckets instead of media pairs; equal hashes have known zero distance and materialize at most eight deterministic non-exact peers per item. A transaction reads at most 128 buckets, one item advances at most 512 buckets per step, and one worker run examines at most 1,024 buckets while fingerprinting at most eight items. `similarity_scan` persists the hash-key cursor after every page. Visual rows use a canonical lexical orientation and retain only the nearest eight outgoing rows per owner, ordered by distance and peer ID. The global relation bound is therefore `8 × catalog size` (800,000 rows for 100,000 eligible items), including flat or common hashes.

Room also persists a library revision, tranche number, distinct non-equal bucket comparison count and continuation count. The automatic chain is limited to eight jobs and 8,192 comparisons for one tranche, including every eligibility revision that occurs during it. A reservation is committed before a scan, so a crash can under-use but cannot exceed the comparison budget. When either limit is reached before complete coverage, status becomes `PAUSED`. That state is a durable hard gate: startup, periodic and catalog invalidation requests neither reset counters nor enqueue a new one-shot chain, and a running worker checks it before every reservation and candidate page. Pause is stored before unique work is cancelled. Only the explicit manual action opens a new bounded tranche and resets its counters. The UI reports current processed/current eligible `SAFE` coverage and the incomplete state, without counting hidden media. An item is marked complete only after every candidate bucket in its cursor domain was checked, so Hamming≤14 recall is retained for all claimed-complete items.

`SimilarityWorker` streams digests with a 64 KiB buffer. Automatic work requires charging and checks battery, storage and severe thermal state; More exposes explicit run and pause controls. Revision-scoped success/failure rows and the durable scan cursor make restart idempotent. Room computes eligible, completed and failed counts in one transaction from current `SAFE` rows only. It records COMPLETE only when every item in that snapshot has a current v2 fingerprint with completed relation scan and no current failure. Catalog/exposure invalidation schedules another bounded pass, so a concurrent eligibility change cannot leave a stale complete state.

Publication and visible reads require `AVAILABLE`, no trash timestamp, current revision/access epoch and explicit `SAFE` exposure. Room triggers advance the eligible-library revision only when an item enters or leaves that exact membership, or when the identity/content/access token of an item eligible on both sides changes. `QUARANTINED`↔`SENSITIVE`, non-SAFE insert/delete, changes outside the eligible set, no-op upserts and routine scan bookkeeping preserve the current revision, ready flags and visual rows. Media and exposure insertion or deletion in either order contributes one membership transition rather than two. A real domain change invalidates non-paused checkpoint completion without resetting tranche or budget counters and never clears `PAUSED`. Every visual scan, endpoint readiness marker and relation is tied to that revision. A changed domain immediately hides prior visual rows, restarts partial cursors, and queues every eligible owner for bounded deterministic top-eight recomputation; a former ninth neighbor can therefore be promoted when a nearer row becomes hidden. Exact SHA groups remain revision/access-bound and survive this visual regeneration. Unclassified, sensitive, inaccessible, missing, trashed, changed, clipped, corrupt or revoked media cannot enter results or actions.

Both the organization surface and comparison screen observe media, exposure, fingerprint, failure, band, scan, relation and checkpoint invalidations. Exact-group and visual-pair lists have independent cursors and controls. Comparison invalidation synchronously re-queries only its current pair; unrelated indexing churn leaves decoded previews intact. It reloads only when the shown pair token changes, and revalidates on start, resume, before every bind and before every action. If either endpoint stops being current and `SAFE`, it immediately recycles both previews, clears metadata and actions, and shows only the unavailable state.

The EN/RU UI lists exact groups with paged members and visual relations with bounded previews, source, dimensions, byte size and reason. It exposes deletion only for an available private import and routes confirmation through the existing 30-day trash. Device and Google Photos originals are read-only. Lik never chooses a preferred original, merges records or deletes a file automatically.

Room schema v14 binds fingerprint readiness, scans and visual relations to the current library revision. Its migration discards regenerable visual cursors/edges while preserving SHA fingerprints, exact groups and any durable `PAUSED` checkpoint with its tranche/comparison/continuation counters. A migrated pause remains closed to non-manual startup work until explicit resume. Schema v13 added the durable library-revision/tranche budget to `similarity_checkpoint` plus trigger-maintained `similarity_library_state`; schema v12 added `similarity_scan` and invalidated v1 bands and visual relations. The earlier v10→v11 migration introduced the remaining fingerprint/relation tables. All migrations preserve catalog identity and user organization data.
